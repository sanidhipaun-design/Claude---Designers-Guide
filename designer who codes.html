Chapter 01 — The Journey

Life was simple.
Then came Claude.

Here's how a designer goes from zero to "oh, I actually understand what's happening."

Before Everything

I lived entirely in Figma. Frames, auto-layout, components, variables. HEX codes were as technical as it got. "The developers will handle the rest" was my whole plan.

The closest I got to code was inspecting a CSS value in the Dev Mode panel and immediately closing the tab.

Day 1 with Claude

Someone said "just prompt it, it'll do everything." So I typed what I wanted. Claude wrote something back that looked like total gibberish — but then it appeared on screen exactly as I imagined it. That felt like magic.

Claude asked if I wanted to "push it to GitHub". I said yes. I had absolutely no idea what that meant.

Week 1

I started noticing words I didn't understand: Git, npm, Tailwind, component, deploy, localhost, terminal, TypeScript. I nodded and clicked approve on everything. The imposter syndrome was real.

I genuinely thought "terminal" was just what they called the app because it looked scary.

Week 3

I started asking Claude to explain what it was doing, not just do it. That changed everything. Turns out, most coding concepts are just design concepts with different names.

The biggest revelation: a React component is basically a Figma master component. I already understood components.

Now

I know what the words mean. I know what Claude is doing when it does it. I'm not a developer — but I'm a much better collaborator, a better prompter, and honestly a better designer for it.

Chapter 03.5 — Before You Begin

The setup that saves
everything.

The single biggest mistake I made early on: starting Claude sessions with zero safety net. One long conversation, one error, one "context window full" message — and everything was gone. Here's what to do before you even type your first prompt.

The problem

Claude sessions have a context window — a memory limit. When you hit it, Claude starts forgetting earlier parts of the conversation. If you've been building something across a long session and Claude throws an error or loses context, you could lose hours of work with no way to recover it.

I once spent 3 hours on a session. Claude hit its limit, got confused, and started contradicting its own earlier code. I had nothing saved. I had to start over.

The solution

Set up a GitHub repository before your first session. Every time Claude produces working code, commit it. If Claude loses context or the session breaks, you can paste your saved files back in and continue from exactly where you left off. Your work is never lost.

Think of it like saving your Figma file constantly. Except in code, saving = committing to GitHub.

The pre-session checklist

01

Create a GitHub account (if you haven't)

Go to github.com and sign up. It's free. This is where all your projects will live online — safe, backed up, and accessible from any computer. Think of it as your code's iCloud.

02

Create a new repository for your project

On GitHub, click "New repository." Give it a clear name (e.g. portfolio-site or design-system). Set it to Private if the work is confidential. Click Create — that's your project folder, now with superpowers.

03

Tell Claude about your repo at the start of every session

Start your Claude session by saying: "I'm working on a project stored at github.com/yourusername/your-repo. Please commit any working code to this repo as we go." Claude can connect to GitHub and commit directly — no terminal needed.

04

Commit after every working milestone

Every time Claude finishes something that works — a component, a page, a feature — ask it to commit. Say: "This is working well. Please commit everything with the message 'Add product card component'." That's your save point.

05

If Claude loses context or something breaks — don't panic

Open your GitHub repo, find the last commit that was working, and copy the files. Start a new Claude session and paste in: "Here is where we left off: [paste code]. Continue from here." You lose nothing. You just continue.

What to say when starting a new session

"I'm working on [project name]. The code is saved at github.com/[username]/[repo]. Here's what we've built so far: [paste your latest code or describe what exists]. Today I want to [describe today's goal]. Please commit working changes to the repo as we go."

This one paragraph gives Claude everything it needs: context of the project, access to the history, a clear goal, and a safety instruction. It's the designer brief equivalent for a coding session.

Session gets too long?

Ask Claude to write a "handoff summary" — a brief of everything built so far. Paste this into the new session. Claude picks up exactly where it left off.

Claude gives a confusing error?

Copy the entire error message and paste it in. Say "fix this." Claude almost always knows exactly what went wrong and will resolve it in seconds.

Claude starts contradicting itself?

This means the context window is full. Start a fresh session, paste in your saved GitHub code, and continue. Fresh context = cleaner thinking from Claude.

Chapter 04 — Inside Claude

What is Claude
actually doing?

When you send a prompt, a lot happens before you see a response. Here's the mental model that helped me stop feeling like I was just "pressing a button."

1

It reads your brief

Claude processes your entire message — your words, your tone, the context of the conversation. Like briefing a designer: the more detail you give, the better the result.

2

It decides what to make

Based on your prompt, Claude decides: is this an HTML file? A React component? A bash command? It chooses the right tool for the job — like deciding whether a design needs a frame or a component.

3

It writes the code

Claude generates code token by token — like a designer placing objects, adjusting spacing, picking colours — but in text. It applies conventions, best practices, and the constraints you gave it.

4

It explains and checks in

Claude almost always tells you what it did and asks if you want changes. This is the equivalent of a designer presenting a frame and asking for feedback. Treat it like a collaboration, not a vending machine.

Real session — designing a card component

Added both. The skeleton uses an animated shimmer effect. For sold out: pass soldOut={true} — the button greys out and shows "Sold out" text. I've also disabled the click event so there's no accidental add-to-bag.

Chapter 06 — Real Lessons

What actually changes
when you understand this.

  • 1

    Your prompts get dramatically better

    When you know what a component, a prop, or a CSS variable is — you can ask for exactly what you want. "Make a Button component that accepts a variant prop of 'solid' or 'ghost'" gets you infinitely better results than "make a button but also a transparent one."

  • 2

    You stop being scared of error messages

    Error messages are just code's way of saying "something's missing or wrong here." You don't need to read them — just paste them directly into Claude and say "fix this." But knowing terms like 'undefined variable' or 'missing import' helps you understand the conversation.

  • 3

    You become a real design-dev bridge

    Developers respect designers who speak some code. Not because you need to write it — but because you can give accurate feedback: "the padding on that component needs to be a multiple of 8" or "that should be a prop, not hardcoded."

  • 4

    Git is just Figma version history — take it seriously

    You would never not save your Figma file. The equivalent in code is committing. When Claude makes commits, those are your save points. A good commit message is like a good Figma frame name — it's for future-you.

  • 5

    Claude works best as a collaborator, not an oracle

    The best sessions I've had are when I treat Claude like a junior dev on a team: give context, give constraints, give feedback. "This spacing is off" or "the hover state should feel more playful" — your design language translates directly.

  • 6

    Your visual eye is a superpower in code

    Most developers don't naturally care about 4px vs 8px of margin. You do. That instinct — noticing when spacing feels off, when a font-weight is too heavy, when a transition is too slow — is incredibly valuable and not something code automatically provides.
